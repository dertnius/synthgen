Bringing a new table under repair

The whole process, from noticing bad data to a run that can be audited and undone — worked on two new tables, dbo.House and dbo.Apartment. Colour tells you who acts: human deterministic code ai. The AI lane proposes; it never disposes.

1 · The two tables

Both need the same three kinds of repair. The interesting part is that the derived rule uses a different formula on each — which is precisely why a rule declares exactly one table and its predicate is not allowed to reach outside it.

dbo.House

HouseId      int          PK
SecurityId   nvarchar(24) NULL   ← identity
Rooms        int          NULL
Bathrooms    int          NULL   ← derived
EnergyClass  varchar(2)   NULL   ← ephemeral

Bathrooms = max(1, ceil(Rooms / 3))
One bathroom minimum, one more per three rooms.

dbo.Apartment

ApartmentId  int          PK
SecurityId   nvarchar(24) NULL   ← identity
Floor        int          NOT NULL
Rooms        int          NULL
Bathrooms    int          NULL   ← derived
HeatingType  varchar(16)  NULL   ← ephemeral

Bathrooms = Rooms >= 5 ? 2 : 1
A flat rarely has three, however many rooms.

Each table also has one row whose Rooms is NULL. Those cannot be derived, and the process is built to leave them alone rather than guess — you will see them again at the gate and in verify.

3 · Stage by stage

human Notice the bad data

A consumer test fails, a DBA flags a column, an import looks wrong. pfandwerk does not decide that anything is broken — it repairs rows matching a predicate somebody wrote, and "this column is wrong" is a judgement, not a measurement.

For the two tables: houses and flats are arriving with no security reference, no bathroom count, and no energy class or heating type.

What it can do is show you the shape of the data so the judgement is informed — that is the next stage.

deterministic pfandwerk survey — profile the tables 
pfandwerk survey --tables dbo.House,dbo.Apartment   # omit --tables for everything
SURVEY dbo.House       200 rows, 6 columns, 5 unruled column(s) with signals
         SecurityId       5% NULL
         Bathrooms        33% NULL; '2' in 50% of non-NULL rows — dominant
         MiddleName       50% NULL; single value across the whole table

Read-only. It writes survey.json — per column: type, nullability, NULL rate, distinct count, the most frequent values, and whether a rule already covers it.

Observations, never verdicts. "EnergyClass is 25% NULL" is a measurement. "EnergyClass is broken" is a judgement, and judgement belongs to whoever writes the rule and approves the run. The survey deliberately does not recognise domain sentinels either — it cannot know that 'X9' means anything, so it reports the distribution and lets a person see the odd one out.

A key column says nothing, and a column an existing rule already covers is marked so nobody drafts a second rule for it.

ai Draft rules from the survey 
copilot -p prompts/draft-rules.md \
  --available-tools=shell,write --allow-all-tools \
  --add-dir "$PWD/rules/drafts" --deny-url --no-color

Reads survey.json, writes proposals to rules/drafts/. This is the one place an agent earns real leverage: writing thirty gap predicates for ten new tables is the actual bottleneck. Generating A+ never was.

A draft is not a rule. The directory is gitignored, you edit the drafts down, and you move what survives into rules/gaps.yaml yourself. The agent is told to default to ephemeral and to justify any identity proposal in a comment — but that is an instruction, not a boundary.

The boundary is what happens next: even after you move a rule across, it clears four independent checks before a row changes — the predicate is parsed and rejected if it references another table, the columns are validated against the live schema, the threshold blocks an over-broad predicate, and you read the frozen values at the gate. That is why an agent is allowed to draft here at all.

human Edit the drafts into rules

Six rules — three kinds across two tables. Only the two derived ones differ in substance:

- id: HOU-001                       - id: APT-001
  table: dbo.House                    table: dbo.Apartment
  key: HouseId                        key: ApartmentId
  column: Bathrooms                   column: Bathrooms
  kind: derived                       kind: derived
  gap: "Bathrooms IS NULL"            gap: "Bathrooms IS NULL"
  fix: house.bathroomsFromRooms       fix: apartment.bathroomsFromRooms
  inputs: [Rooms]                     inputs: [Rooms]
  onMissingInput: block               onMissingInput: block
  threshold: 500                      threshold: 500

Four fields carry the weight, and all four are judgement:

fieldwhat you are deciding
gapWhich rows are wrong. Only you know this. Too loose and you patch good rows.
kindidentity is a one-way door — the value enters the ledger and every future run reuses it.
thresholdYour alarm. Above it the rule is BLOCKED and the gate refuses. Set it near what you expect.
reasonPrinted verbatim at the gate and in the report. Write it for whoever reviews at 5pm on a Friday.
A predicate may only reference its own table. A subquery reaching elsewhere is rejected when the rules load — checked by walking the parsed SQL, not by trusting the author.
human Add a generator, if none fits

Check first — this costs nothing and usually ends here:

pfandwerk generators

Around forty entries already exist. EnergyClass and HeatingType are small fixed sets and the two Bathrooms formulas are per-table, so this example needs four new ones. That is C#, a unit test, and a merge request.

The rule file can never contain a literal value. If it could, "all values come from the code-side whitelist" would stop being true. That is the whole reason a new generator is a code change.

Whoever approves that MR must not be whoever approves the run — the notary fails the build if the approver is the last person to have changed the rules file.

deterministic pfandwerk plan — guard, scan, freeze 
./run.ps1 -Only HOU-001,HOU-002,HOU-003,APT-001,APT-002,APT-003

Three things happen, in order, with no model anywhere near them:

  1. Guard — the connection must match allowlist.json on server, database and auth mode, or the run stops at exit 4 having touched nothing.
  2. Scan — each predicate is parsed, turned into SQL by one shared code path, and executed.
  3. Freeze — every value is generated now and written into plan.json as a literal.
PLAN HOU-001   OK       31 gaps,  29 to patch, 2 skipped, 0 new identities
PLAN HOU-002   OK       12 gaps,  12 to patch, 0 skipped, 12 new identities
PLAN APT-001   OK       44 gaps,  43 to patch, 1 skipped, 0 new identities
PLAN baseline: 2 invariant, 3 consumer already failing
PLAN sha256 7f3a91c4…
That baseline line is the most important output of the run, and the easiest to skim past. It is the state of the world before anything changed. Nothing listed there can be blamed on this run — and anything that goes red later and is not listed, can.

Writes plan.json and baseline.json. Nothing else has changed.

ai Plan summary — optional prose 
copilot -p prompts/plan.md \
  --available-tools=shell,write --allow-all-tools \
  --add-dir "$PWD/artifacts" --deny-url --no-color

Reads plan.json, writes artifacts/plan-summary.md. Useful when the gate output runs to ninety lines and you want the shape before the detail.

It cannot reach a database, and the boundary is not the prompt. Prompts are instructions, and a model that ignores instructions is not misbehaving in a way instructions prevent. The boundary is --available-tools limiting what it can see, --add-dir limiting where it can write, and --deny-url closing the network. Run with -NoAgents and the run is still complete.
human The gate — the one decision 
=== GATE — run 20260815T141133Z-c8e2 ===

HOU-002  identity  dbo.House.SecurityId   [OK]
  12 gaps, threshold 50
  TIER 1 — new identities (PERMANENT, reused by every future run):
    HouseId 4102 -> DE000K7M2P41
    HouseId 4118 -> DE000R3X9T05
    … all 12 listed, never truncated

HOU-001  derived  dbo.House.Bathrooms   [OK]
  31 gaps, threshold 500
  TIER 2 — values to be written:
    HouseId 4102 (Rooms 7)  -> 3
    HouseId 4118 (Rooms 4)  -> 2
  SKIPPED HouseId 4210: input 'Rooms' is NULL  [onMissingInput: block]

APT-001  derived  dbo.Apartment.Bathrooms   [OK]
    ApartmentId 9007 (Rooms 5) -> 2
    ApartmentId 9011 (Rooms 3) -> 1
  COVERAGE
    3 rows breaking the invariant but not selected by the gap — predicate may be too narrow
      ApartmentId 9040, 9052, 9061

Approve? [yes/no]

Five things are in front of you, in order of how expensive they are to get wrong:

whatwhy it is shown that way
Tier 1, in fullPermanent. Truncating the list would make the review theatre.
Inputs beside outputs3 alone is uncheckable. Rooms 7 → 3 is checkable at a glance — and note the flat with 5 rooms gets 2 while the house with 7 gets 3, because the formulas differ.
Skipped rowsApproving accepts that those stay broken. That is a decision, made by proceeding.
[BLOCKED]Any rule past its threshold refuses the whole run. Look before raising the number.
COVERAGEThe only line that checks the rule against the data rather than against the schema. Advisory — it never blocks.
Coverage cross-checks the gap against the rule's own invariant, and appears only when the two disagree. Rows broken by your definition that the gap does not reach mean the predicate is too narrow; rows it selects that the invariant already accepts mean it is too broad; rows the invariant cannot evaluate at all — a NULL in a column it references — mean verify will pass them in silence. Every other check validates a rule's shape. This is the one that asks whether it selects what you meant.
Those are the real values. They were generated before you were asked and frozen into plan.json; the SHA-256 you approve covers them, and apply re-checks that hash before writing. What you see is what lands.
deterministic pfandwerk apply — the only step that writes

First it recomputes sha256(plan.json) and compares it to plan.approved. It does not trust that the gate ran — a plan edited after approval is rejected even if the scripts ran in the right order.

Then, per row, in one transaction each:

ledger INSERT  (identity rules only)   ┐ both commit,
target UPDATE                          ┘ or neither
APPLY 96 rows patched via sql -> artifacts/patches.jsonl

patches.jsonl records the old value of every column touched. That is what makes the run reversible — without it there is nothing to restore.

deterministic pfandwerk verify — three layers, diffed 
VERIFY L1 pass  L2 pass  L3 pass
  regressions:            none
  pre-existing failures:  HOU-001.invariant, APT-001.invariant, House.HasSecurityId
layerchecksexit if it fails
L1Every row the plan promised to patch no longer matches its predicate. Skipped rows are not in that set, so they cannot fail it.10
L2Each rule's invariant, across the whole table — not just patched rows. Every row the invariant can judge: see below.20
L3The consumer suite.30
Regressions and pre-existing failures are never merged. A regression is something this run broke — green before, red now. A pre-existing failure was already red when the baseline was captured: it is listed and it does not fail the run. Here the three rows with NULL Rooms keep both invariants red, and that is correct.
A green L2 does not mean every row was checked. The query is NOT (invariant), and SQL is three-valued: a NULL in any column the invariant references makes it UNKNOWN, which is neither a violation nor a pass, so the row is skipped over. When that happens the check's detail in verify.json says how many — 4 row(s) not evaluated. The fix is a NULL-safe invariant (Column IS NOT NULL AND …), not different data.

Exit 0. Writes verify.json.

ai + deterministic pfandwerk report

The agent writes prose; code decides whether it ships.

copilot -p prompts/report-maker.md …     # writes artifacts/report.md
pfandwerk report                          # facts → audit → fallback

report extracts facts.json deterministically, then checks every number and rule id in the prose against it. One invented figure and the narrative does not ship — you get a bare rendering of facts.json instead.

There is no second model checking the first. Mechanical number-matching is what code does perfectly and a model does probabilistically, and that code had to exist for the notary anyway.
deterministic pfandwerk notary — in CI

No database, no Copilot, committed artifacts only. It re-checks:

  • sha256(plan.json) against plan.approved
  • the rules hash the plan was built from, against the rules in the tree
  • facts.json against a fresh extraction from patches.jsonl
  • report.md against facts.json
  • four eyes — the approver is not whoever last changed rules/gaps.yaml
Scope, stated plainly: this proves a file set produced by one person is internally consistent. It catches drift, a stale report and an unapproved plan. It does not defend against someone editing patches.jsonl and facts.json together.
human Undo, if you need to 
pfandwerk revert                  # everything, newest first
pfandwerk revert --only HOU-001   # one rule

Local only, never CI. Replays patches.jsonl backwards through the same write path that applied it.

The ledger rows stay. After a revert the twelve houses have no SecurityId again — but the ledger still records which reference belongs to each. The next run looks there first and writes back DE000K7M2P41, not a new one. Deleting those rows would make "frozen forever" false the first time anyone reverted.

4 · The three kinds, side by side

ephemeralidentityderived
House EnergyClass SecurityId Bathrooms = ceil(Rooms/3)
Apartment HeatingType SecurityId Bathrooms = Rooms≥5 ? 2 : 1
value comes from the whitelist, frozen at plan time the whitelist, then collision-checked against table and ledger a pure function of the columns in inputs
ledgernoyes — permanentno
survives a revert no, regenerated yes, identical value no, recomputed — same answer, because the function is pure
checkable afterwards no uniqueness only yes — a full-table invariant

That last row is the practical payoff of a derived rule. Because the value is a function of the row, correctness can be asserted over every row in the table, not only the ones this run touched — which is why the derived rules carry an invariant and the other kinds do not.

5 · When it does not go straight through

stops Threshold exceeded

More rows matched than the rule allows, so it is BLOCKED and the gate refuses the whole run. Either the data degraded or your predicate is too broad. Look before raising the number.

yours Row cannot be derived

Rooms is NULL, so onMissingInput: block leaves the row alone and lists it. Fix Rooms upstream, or change the policy to floor via another MR. Approving proceeds without it.

stops Regression

A check that was green at baseline is now red. Exit 20 or 30, and it stops. This is the only failure the run attributes to itself.

yours Predicate may be too narrow

COVERAGE at the gate: rows break the invariant that the gap does not select. Advisory, unlike the stop-shaped cards here — it prints and the run continues, because a row nothing can repair is a legitimate instance. Widen the predicate, or accept it by approving.

fine Pre-existing failure

Red before, red after. Listed, never fatal. Without a baseline this would look like damage the run caused and would block every future run.

stops Ledger conflict

The ledger already records a different value for that row and column. Exit 5. Ledger rows are never updated, so a person has to decide.

stops Not allowlisted

The connection does not match allowlist.json. Exit 4, before anything is read or written. The last thing between a mistyped server name and a patched table.
